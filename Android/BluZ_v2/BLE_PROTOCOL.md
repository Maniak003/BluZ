# BluZ BLE Protocol

## Подключение

| Параметр | Значение |
|---------|---------|
| Транспорт | BLE (Bluetooth Low Energy) |
| MTU | 251 байт (запрашивается при подключении) |
| Payload | MTU − 3 = 248 байт |
| Приоритет | `CONNECTION_PRIORITY_HIGH` |

**UUIDs:**
```
Service:    0000fe80-cc7a-482a-984a-7f2ed5b3e58f
RX (нотиф): 0000fe81-8e22-4541-9d4c-21edae82ed19  ← устройство → телефон
TX (запись): 0000fe82-8e22-4541-9d4c-21edae82ed19  ← телефон → устройство
```

Для получения данных включаются нотификации на RX-характеристику через дескриптор CCCD (`00002902-0000-1000-8000-00805f9b34fb`).

## Рукопожатие (hw info)

После включения нотификаций приложение отправляет команду 10 (hw info) и до ответа игнорирует
все остальные фреймы. Прибор отвечает фреймом `frameType = 7` из одной нотификации, содержащей
только заголовок (без данных дозиметра, лога и спектра). Байт 6 — мажорная версия протокола,
байт 7 — минорная. Положение этих байтов обязано оставаться неизменным во всех версиях протокола,
остальной формат фреймов может меняться между мажорными версиями. Изменение минорной версии не
ломает взаимодействие приложения и прибора, а только добавляет новые команды, возможности
(например, термокомпенсацию) и т.п.

Статус «подключено» приложение выставляет только после ответа с поддерживаемой версией. Сразу после этого
оно включает автонотификацию (команда 13, интервал в байте 4). Бит 0 байта 5 (`forceSpectrum`) просит ответить кадром со спектром: приложение
ставит его, если в байтах 90–93 ответа hw info (счётчик импульсов спектрометра) не ноль; иначе ответ — кадр по состоянию прибора
(дозиметр, а у работающего спектрометра ещё и спектр). Ответ на команду 13 — первый кадр, интервал в его байте 8 приложение не проверяет.
Отдельные команды 11 и 12 в рукопожатии не нужны.
Совместимость приложение проверяет только по мажорной версии, минорная пишется в лог (`мажорная.минорная`)
при успешном рукопожатии как диагностика. Приложение работает только с мажорной версией 1. Иначе оно пишет
пользователю, игнорирует данные и не отправляет команды (соединение не разрывается):
- нет ответа (проверяется тиком таймера переподключения, отказ через 6–16 с после запроса) — прошивка не поддерживает hw info, обновить прибор;
- мажорная версия больше 1 — обновить приложение;
- мажорная версия меньше 1 — обновить прибор.

## Формат входящего пакета

Полный пакет передаётся несколькими MTU-фрагментами.

### Первый фрагмент (заголовок пакета)

| Смещение | Размер | Тип | Содержимое             |
|---------|--------|-----|------------------------|
| 0 | 1 | byte | `0x3C` (`<`) — маркер начала |
| 1 | 1 | byte | `0x42` (`B`) — маркер начала |
| 2 | 1 | byte | `0x3E` (`>`) — маркер начала |
| 3 | 1 | byte | `frameType` (0–7)      |
| 4 | 1 | byte | флаги: бит 0 — запрет тревоги, бит 1 — спектрометр запущен (приложение берёт состояние кнопки Start/Stop отсюда, а не из типа фрейма) |
| 5 | 1 | byte | `dataSize` — число MTU-фрагментов в кадре (приложение собирает кадр по нему) |
| 6 | 1 | byte | мажорная версия протокола (сейчас 1) |
| 7 | 1 | byte | минорная версия протокола (сейчас 0) |
| 8 | 1 | byte | интервал автонотификации, секунды; 0 — автонотификация выключена |
| 9 | 1 | — | зарезервировано        |
| 10 | 4 | uint32 LE | `totalPulses` — суммарный счёт импульсов |
| 14 | 4 | uint32 LE | `pulsesPerSec` — импульсов за последнюю секунду |
| 18 | 4 | uint32 LE | `measurementTime` — время измерения, секунды |
| 22 | 4 | float32 LE | `avgCps` — скользящее среднее CPS |
| 26 | 4 | float32 LE | `temperature` — температура SiPM, °C |
| 30 | 4 | float32 LE | `batteryVoltage` — напряжение батареи, В |

### Количество фрагментов по типу пакета

Фактическое число фрагментов кадра передаётся в байте 5 заголовка. Размер кадра со спектром зависит от формата спектра (байт 96), в таблице — размер при несжатом спектре (максимум для типа).

| frameType | Описание                 | Фрагментов | Итого байт |
|-----------|--------------------------|------------|------------|
| 0         | Только дозиметр          | 6          | ~1 488     |
| 1         | Дозиметр + спектр 1024   | ≤ 23       | ≤ ~5 700   |
| 2         | Дозиметр + спектр 2048   | ≤ 40       | ≤ ~9 760   |
| 3         | Дозиметр + спектр 4096   | ≤ 73       | ≤ ~17 800  |
| 4         | Дозиметр + история 1024  | ≤ 23       | ≤ ~5 700   |
| 5         | Дозиметр + история 2048  | ≤ 40       | ≤ ~9 760   |
| 6         | Дозиметр + история 4096  | ≤ 73       | ≤ ~17 800  |
| 7         | Информация об устройстве (только заголовок) | 1          | ~248       |

### Структура каждого фрагмента

- **Не последний:** `[payload 243 байта][footer 5 байт]`
- **Последний:** `[payload][2 байта checksum LE][5 байт footer]`

Контрольная сумма — сумма всех payload-байт всех фрагментов (UShort, Little-Endian).

## Формат спектра

Отсчёты каналов — `uint32` без потерь. Формат задаёт байт 96 заголовка:

- `0` — отсчёты как есть, `uint32` little-endian, 4 байта на канал;
- `1` — DPCM + ZigZag + varint: для каждого канала считается разность с предыдущим (по модулю 2^32, перед первым каналом `prev = 0`),
  затем ZigZag `(d << 1) ^ (d >> 31)`, затем varint base-128 (младшая группа первой, бит 7 — признак продолжения).
  Пример: `[0, 1, 0, 65]` → `00 02 01 82 01`.

Прошивка берёт сжатый формат, только если он строго меньше несжатого (`4 × N` байт), иначе передаёт формат 0.
Данные спектра начинаются со смещения 1424; после них до контрольной суммы кадр заполнен нулями.
Число фрагментов кадра — в байте 5.

## Команды (телефон → устройство)

Команда отправляется как пакет 244 байта:

```
Byte 0:   '<'  (0x3C)
Byte 1:   'S'  (0x53)
Byte 2:   '>'  (0x3E)
Byte 3:   cmd  (код команды)
Bytes 4-241:   payload (заполнен из sendBuffer)
Byte 242: CS низкий байт (сумма байт 0-241, uint16 LE)
Byte 243: CS высокий байт
```

Известные коды команд (из исходников NumberFragment):
- `6u` — "Find" (поиск/пинг устройства)
- `10u` — запрос hw info (ответ — фрейм типа 7 с версией протокола)
- `11u` — запрос кадра со спектром (ответ — фрейм типа 1..3 по текущему разрешению, даже если спектрометр выключен)
- `12u` — запрос кадра дозиметра (ответ — фрейм типа 0, даже если спектрометр включён)
- `13u` — интервал автонотификации: байт 4 — секунды (0–255), 0 — выключить; байт 5, бит 0 (`forceSpectrum`) — ответить кадром со спектром, как на команду 11 (иначе кадром по состоянию прибора). Ответ несёт в байте 8 новое значение
- Остальные коды — в прошивке устройства

### Ответы на команды

Кроме ответов на команды прибор может сам слать автонотификацию — кадр текущего режима (тип 0..3) с интервалом,
заданным командой 13. После подключения интервал равен 0 и автонотификации нет, пока клиент её не включит;
интервал не хранится во flash. Текущее значение — в байте 8 каждого кадра.
Ответ на команду уходит, не дожидаясь очередной автонотификации: на ближайшем проходе главного цикла прошивки.
Между проходами процессор спит до следующего прерывания (например, секундного таймера измерений), поэтому до начала
ответа проходит до ~1 с:

- hw info (10) — кадр типа 7;
- запрос истории (5) — кадр истории (типы 4..6);
- запрос спектра (11) — кадр со спектром (типы 1..3); бит «спектрометр запущен» в нём отражает реальное состояние;
- запрос дозиметра (12) — кадр типа 0;
- остальные команды (настройки, старт/стоп спектрометра, очистки, поиск, запрет тревоги, калибровка батареи) —
  внеочередной кадр с новым состоянием (в том числе при выключенной автонотификации).

Несколько команд подряд дают очередь ответов: все они уходят в ближайших циклах передачи, по одному кадру
за проход (hw info, история, спектр, дозиметр, автонотификация); перед каждым следующим кадром возможна такая же пауза до ~1 с.
Одинаковые ответы не повторяются: две команды, требующие автонотификацию, дают один кадр.

Любой кадр заменяет плановую автонотификацию: интервал отсчитывается заново от конца передачи кадра.
Если кадр передавался дольше интервала, плановый кадр пропускается, а не идёт следом.

## Очередь записи (writeBuffer)

Большие команды разбиваются на чанки по `payloadSize = 248` байт.
Отправка сериализована: следующий чанк уходит только после
`onCharacteristicWrite` от предыдущего.

```
write(data)
  ├── если data.size ≤ 248: прямая запись (если нет pending)
  ├── иначе: нарезать на чанки → добавить в writeBuffer
  └── writeNext() вызывается из onCharacteristicWrite
```

**Исправленная логика writeNext()** (был баг двойного удаления):
```kotlin
synchronized(writeBuffer!!) {
    data = if (writeBuffer!!.isNotEmpty()) {
        writePending = true
        writeBuffer!!.removeAt(0)   // единственное удаление внутри lock
    } else {
        writePending = false
        null
    }
}
```
